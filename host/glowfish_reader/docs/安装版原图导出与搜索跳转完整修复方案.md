# 安装版原图导出与搜索跳转完整修复方案

## 1. 文档目标

修复 Glowfish Reader V1.0.0 安装版中的两个问题：

1. 选择页面并勾选“附带原图”导出时，提示：

   > 导出失败：已选择“附带原图”，但所选页面没有可用原图，请重新导入或检查原图文件。

2. 搜索能够返回正确文本，但点击搜索结果定位时，提示：

   > 打开失败：Document not found

本方案覆盖根因、代码修改、旧数据兼容、测试补强、打包发布和安装版验收。修复不得破坏现有校对文本、批注、笔记本结构及原图文件。

---

## 2. 排查结论

两个问题均为当前源码和 V1.0.0 安装包中的接口契约缺陷，不是用户文档损坏。

| 问题 | 直接根因 | 结论 |
|---|---|---|
| 选择页面附带原图导出失败 | 前端提前聚合页面，但没有保留每页所属 `batch` 和 `image_dir`；后端无法解析 `_img/...` 等相对路径 | 前后端导出请求契约不一致 |
| 搜索结果点击失败 | 后端返回命中字段 `batch`，前端跳转读取 `h.docId` | 搜索响应字段不一致 |

只读核验结果：

- 当前安装版数据目录中共有 35 份 `proof.json`。
- 所有页面均能在各自 `_src` 目录找到对应原图；不需要重新导入。
- 笔记本登记的 33 份文档均存在，没有发生搜索索引指向已删除文档的问题。
- 安装目录中的 `app.js`、`search.js` 与当前构建目录文件哈希一致，证明问题已进入当前 V1.0.0 安装产物。
- 使用安装版真实数据复现：
  - 按当前前端请求格式导出，稳定返回 HTTP 422。
  - 改用后端已有的 `selected: [{batch, page_ids}]` 格式，返回 HTTP 200，DOCX 正确嵌入原图。
  - 同一文档按笔记本范围导出，返回 HTTP 200，并正确嵌入全部图片。

## 3. 问题一：附带原图导出失败

### 3.1 当前错误调用链

选择页面导出时，`static/app.js` 的 `selectedPagesExportBody()` 会在前端加载各文档，并提前合并为一个临时 proof：

```js
{
  scope: "selected_pages",
  proof: {
    batch: "selected_pages",
    source: "...",
    script: "s",
    engine: "merged",
    pages: [...]
  },
  page_ids: [...]
}
```

合并后的页面不再携带其来源文档的 `image_dir`。对于常见的页面图片值：

```text
_img/0001_10.jpg
```

后端无法知道它应当相对于哪个 `<batch>/_src` 目录寻找原图。

`export_api._export_selected()` 实际已经支持更正确的请求格式：

```json
{
  "scope": "selected_pages",
  "selected": [
    {"batch": "10", "page_ids": ["0001_10"]}
  ]
}
```

但当前前端没有发送 `selected`，所以正确分支没有被使用。

### 3.2 前端修复

修改 `proofread/static/app.js`：

1. `selectedPagesExportBody()` 不再加载或聚合 proof，只构造来源明确的选择列表。
2. 发起导出前调用 `await gfAwaitSave()`，保证当前校对内容已经写入磁盘。
3. 请求体改为：

```js
async function selectedPagesExportBody(selected, pageMarks) {
  const nb = (typeof nbCur === "function") ? nbCur() : null;
  return {
    scope: "selected_pages",
    selected,
    name: (nb && nb.name) || "选中页面",
    page_marks: pageMarks,
  };
}
```

4. `doExport()` 在调用 `downloadExport()` 前执行：

```js
if (typeof gfAwaitSave === "function") {
  await gfAwaitSave();
}
```

5. `loadProofForExport()` 若不再被其他功能使用，应删除，避免再次出现前端聚合和磁盘数据不一致。

### 3.3 后端修复

修改 `proofread/export_api.py`：

1. 将 `selected` 作为选择页面导出的正式接口契约。
2. 对每个 `{batch, page_ids}`：
   - 使用 `ctx.reg(batch)` 获取真实 `proof_path`。
   - 从磁盘读取该文档最新 `proof.json`。
   - 按 `page_ids` 过滤页面。
   - 在聚合前解析并固定该页真实原图路径。
3. 旧版聚合请求因为已经丢失来源信息，不能通过 `page_id` 在全库中猜测来源；不同文档可能存在相同 `page_id`。因此不要做模糊恢复。
4. 对不带 `selected` 的旧聚合请求返回明确错误，例如 HTTP 409：

```json
{
  "detail": "client_outdated: 请升级或重启应用后重新导出"
}
```

这比误报“没有原图”更准确，也能提示 WebView 仍在使用旧缓存。

### 3.4 统一原图解析器

当前 `page_image_path()` 同时承担查看底图、DOCX 插图和导出原图解析，候选顺序可能把旧数据中的绝对 `_img/*.jpg` 预览图当成原图。

应新增语义明确的导出解析器，例如：

```python
resolve_original_page_image(proof, page, proof_path)
```

候选顺序：

1. 当前文档真实目录 `<batch>/_src`。
2. 合法且位于数据沙箱内的 `proof.image_dir`。
3. 使用 `page.image` 文件名、文件 stem、`page_id`，在上述目录依次匹配：
   - `.png`
   - `.jpg`
   - `.jpeg`
   - `.tif`
   - `.tiff`
   - `.bmp`
   - `.webp`
4. 只接受 `safefs.within_work()` 校验通过的文件。
5. `_img` 只能作为页面预览兜底，不应在“附带原图”中静默替代 `_src` 原件。

聚合后，将已确认的原图固定为页面的沙箱内绝对路径，再交给 DOCX 或 ZIP 生成器，防止跨多个文档时再次丢失上下文。

### 3.5 缺图策略

当前逻辑只要选中页面中存在一张图片就继续导出，可能产生“导出成功但部分页面缺图”的静默数据缺失。

建议采用严格策略：

- 勾选“附带原图”时，所有选中页面都必须解析到原图。
- 任意页面缺图即返回 HTTP 422。
- 响应包含缺失数量和最多若干个页面标识：

```json
{
  "detail": {
    "code": "export_images_missing",
    "missing_count": 2,
    "pages": [
      {"batch": "10", "page_id": "0003_10"},
      {"batch": "12", "page_id": "0001_12"}
    ]
  }
}
```

前端应将其显示为“2 个选中页面缺少原图”，而不是要求所有场景都重新导入。

## 4. 问题二：搜索结果点击后 Document not found

### 4.1 当前错误调用链

`library_api.library_search()` 返回：

```json
{
  "batch": "10",
  "docName": "...",
  "pageId": "0001_10",
  "pageIdx": 0,
  "lineId": "0001_10__0",
  "start": 3,
  "end": 5
}
```

但 `static/search.js::gotoHit()` 使用：

```js
await nbOpenDoc(h.docId);
```

由于响应中没有 `docId`，实际执行：

```js
nbOpenDoc(undefined)
```

随后产生：

```text
/api/load?batch=undefined
```

后端因此正确返回 `Document not found`。问题不在 `/api/load`，而在调用前丢失了文档标识。

### 4.2 前端修复

修改 `proofread/static/search.js`：

```js
async function gotoHit(h) {
  const docId = h.batch || h.docId;
  if (!docId) {
    toast("搜索结果缺少文档标识，请重新搜索");
    return;
  }

  if (!proof || proof.batch !== docId) {
    if (typeof nbOpenDoc !== "function") return;
    await nbOpenDoc(docId);
  }

  if (!proof || proof.batch !== docId) {
    toast("无法打开搜索结果对应的史料");
    return;
  }

  // 后续定位……
}
```

同时增加异常捕获，避免 `nbOpenDoc()` 失败后产生未处理 Promise。

### 4.3 后端兼容

为兼容 WebView 可能缓存的旧版 `search.js`，补丁版本中后端同时返回：

```python
{
    "batch": batch,
    "docId": batch,
    ...
}
```

兼容周期至少保留一个小版本：

- 新前端优先读取 `batch`。
- 旧前端仍可读取 `docId`。
- 后续大版本再考虑移除 `docId` 别名。

### 4.4 页面和行定位增强

搜索结果生成后，用户可能重新排序页面或编辑文档。定位时不应只相信旧的 `pageIdx`。

推荐逻辑：

1. 打开 `batch`。
2. 优先通过 `pageId` 在当前 `proof.pages` 中查找页面。
3. 找不到 `pageId` 时才回退到 `pageIdx`。
4. 校验 `lineId` 是否仍存在。
5. 行已删除或文本已改变时，提示“搜索结果已过期，请重新搜索”，不要跳到错误位置。

## 5. 缓存与安装版兼容

当前 `static/index.html` 使用固定查询版本：

```html
<script src="app.js?v=20260707-ui"></script>
<script src="search.js?v=20260711-search-ellipsis"></script>
```

安装升级后如果查询版本不变，WebView2 可能继续使用旧脚本。

修复时必须：

1. 更新相关静态资源版本，例如：

```html
<script src="app.js?v=20260713-export-contract"></script>
<script src="search.js?v=20260713-search-contract"></script>
```

2. 建议为 `index.html` 和核心 JS 增加 `Cache-Control: no-cache`，允许缓存但每次启动重新验证。
3. 应用升级完成后彻底退出旧进程，再启动新版本。
4. 保持安装器 AppId 不变，执行就地升级，不删除 `%APPDATA%` 用户数据。
5. 可在安装阶段清理已失效的旧版开始菜单快捷方式，但不得删除旧数据目录。

## 6. 测试补强

### 6.1 原图导出测试

必须覆盖：

1. 单文档选择页面，DOCX 附带原图。
2. 跨文档选择页面，DOCX 每页均嵌入其来源原图。
3. Markdown/TXT/CSV 导出 ZIP 中包含全部原图。
4. 整个笔记本导出。
5. `page.image` 为 `_img/name.jpg`，原图为 `_src/name.png`。
6. 旧绝对 `_img` 路径存在，但 `_src` 也存在时，必须选择 `_src` 原图。
7. `image_dir` 是失效旧路径，但当前 `<batch>/_src` 有原图。
8. 单页缺图和多页部分缺图。
9. 非沙箱路径、路径穿越和外部绝对路径必须被拒绝。
10. 当前前端真实请求体必须包含 `selected`，不得只调用后端内部函数绕过前端契约。

### 6.2 搜索跳转测试

必须覆盖：

1. 后端命中项同时包含 `batch` 和兼容字段 `docId`。
2. 点击搜索结果时，`nbOpenDoc()` 收到正确 `batch`，不能是 `undefined`。
3. 当前文档命中不重复加载。
4. 跨文档命中可以打开并定位。
5. 页面顺序变化后通过 `pageId` 正确定位。
6. 文档、页面或行已删除时显示可理解提示。
7. 搜索和打开过程不触发 OCR、不改写 `proof.json`。
8. 长文档名、简繁互搜、忽略标点、结果截断继续通过。

### 6.3 冻结版发布自检

当前 `_selftest_release_fixes()` 直接调用后端正确分支，因此即使真实前端仍发送错误请求也会通过。

应将发布闸升级为：

1. 使用与前端完全一致的 JSON 请求调用 `/api/export`。
2. 解包 DOCX，断言 `word/media` 中图片数量等于选中页数量。
3. 解包非 DOCX ZIP，断言原图数量、文件名和字节内容正确。
4. 调用 `/api/library_search` 取得真实命中结果。
5. 执行前端跳转契约测试，确认命中项能映射到文档 ID。
6. 对冻结目录中的 `app.js`、`search.js` 执行行为或契约检查，而不只是检查文件存在。
7. 将上述测试加入 `release.ps1`，任何一项失败均禁止生成或发布安装器。

## 7. 建议实施顺序

### 阶段 A：建立失败测试

1. 用当前前端实际请求格式复现选择页面导出 422。
2. 建立搜索 `batch`/`docId` 契约测试。
3. 建立 `_src` 优先于 `_img` 的原图测试。
4. 确认测试在修改前失败。

### 阶段 B：修复代码

1. 修改 `static/app.js`，发送 `selected` 并在导出前刷新保存。
2. 修改 `export_api.py`，正式化 selected-pages 契约和严格缺图策略。
3. 新增统一原图解析器并让 DOCX、ZIP 共用。
4. 修改 `static/search.js`，统一使用 `batch` 并增强定位校验。
5. 修改 `library_api.py`，临时返回 `docId` 兼容别名。

### 阶段 C：回归验证

1. 运行导出、搜索、内容加载、图片修复相关测试。
2. 运行全部 proofread 测试。
3. 使用真实数据副本进行只读/临时目录验收。
4. 验证导出和搜索均不触发 OCR。

### 阶段 D：安装版发布

1. 版本升级为 V1.0.1。
2. 更新静态资源缓存版本。
3. 使用 `PyInstaller --clean` 重新构建。
4. 运行冻结版完整契约自检。
5. 运行 frozen payload audit。
6. 使用 Inno Setup 生成安装器。
7. 在已有 V1.0.0 的机器上覆盖安装并验证用户数据完整。

## 8. 安装版验收标准

发布前必须全部满足：

- [ ] 选择任意单页并附带原图，DOCX 正确包含该页原图。
- [ ] 跨文档选择多页，DOCX/ZIP 中图片数量与选中页数量一致。
- [ ] 整个笔记本导出正常。
- [ ] 原图缺失时明确指出缺失页面，不再笼统要求重新导入。
- [ ] 搜索当前文档并点击，可以定位到正确页面和文字。
- [ ] 搜索其他文档并点击，可以自动打开并定位。
- [ ] 搜索命中点击不再出现 `Document not found`。
- [ ] 搜索和打开既有文档不触发 OCR。
- [ ] 更新安装后旧校对文本、批注、笔记本和原图全部保留。
- [ ] 关闭网络后上述本地功能仍可使用。
- [ ] 安装目录静态文件与构建产物哈希一致。
- [ ] 冻结版端到端自检通过后才允许发布。

## 10. 最终判断

两个故障都不需要通过重新导入史料解决：

- 原图导出失败的核心是选择页面请求在前端聚合时丢失来源路径。
- 搜索跳转失败的核心是后端 `batch` 与前端 `docId` 字段不一致。

修复重点不是继续扩展路径猜测，而是统一前后端数据契约、保留每页来源、建立真实前端到冻结安装包的端到端发布闸。完成本方案后，应以 V1.0.1 安装包覆盖升级并执行真实安装态验收。
